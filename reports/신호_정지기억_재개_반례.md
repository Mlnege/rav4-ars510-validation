# 비활성 후 빨강 정지 기억의 부분 신호 전이 검사

2026-10-12 19:53:53.903~19:53:58.257 KST에 최종 고정 도구를 직접 실행했다. 23조건, 실제 MPC 계획 3,324회, 원형 LongControl 16,620회를 완료했다. 정상 빨강 정지 상태에서 `CarControl.longActive`만 잠깐 끄면 기존 정지 기억이 지워지는 반례가 재현됐다. 500ms 비활성 뒤 빨강으로 재개한 조건에서는 빨강을 다시 확인하기 전 50~100ms 구간에 양수 LongControl 출력이 관측됐다.

이 결과는 새 헤더 보강안을 구현한 시험이 아니다. 전체 호스트의 활성 권한을 도출하지도 않았다. 합성 SelfdriveState/CarControl 입력을 실제 신호 런타임·CarrotPlanner·LongitudinalPlanner·MPC·LongControl에 전달한 부분 검사다. 운영 코드 수정, 실제 차량 송신, Panda/PCS 변경은 없었다.

## 실행과 입력 계약

새 도구 `probe.py`와 같은 내용을 가진 `probe_final.py`를 동결했다. `run03_final/results.json`, 조건별 `plans.csv`/`controls.csv`/`summary.json`이 최종 근거다. `run01`/`run02`는 같은 계산의 초기 실행을 보존했다. 그 뒤 신규 도구의 import/빈 줄 정렬만 정리했으며, 정렬을 마친 도구로 `run03_final`을 다시 실행했다. 원형 계산·기존 도구는 바꾸지 않았다. 최종 Ruff 직접 검사도 오류 없이 종료했다.

모든 조건에서 먼저 5초의 합성 빨강 입력으로 mode2의 정상 context와 빨강 hold를 확보했다. 마지막 기준 입력은 `104.95s`, runtime enabled/valid=True, hold=True, shouldStop=True, 계획 가속 약 `-0.0001436m/s²`, LongControl 최대 출력 약 `-0.5010m/s²`였다. 같은 신호 상자의 좌표·session을 유지했다. 새 신호 물체나 레이더 트랙을 추가하지 않았다.

카메라 metadata는 기존 도구의 tizi/OX03C10 공식 프로파일 합성 fixture다. 이미지를 처리하지 않았고 실제 Konik 인식 정확도·영상·색 분류의 증거가 아니다. 속도/가속은 0으로 고정했고, 모델에는 기본적으로 명시적 미래 진행 의도를 제공했다. 비교 2조건에는 모델 정지 의도를 제공했다. 차량 운동 모델은 실행하지 않았다.

합성 단조 시각으로 계획 50ms마다 한 번, 계획마다 가상 10ms 간격의 원형 제어를 다섯 번 호출했다. 여기서 “1틱”은 **50ms 계획 입력 1틱**이다. 실제 벽시계 100Hz 제어 및 10ms 단독 비활성·20Hz planner가 이를 관찰하지 못하는 경우를 검증한 것으로 해석하면 안 된다. 입력 헤더·수신 metadata·관측 timestamp는 각 합성 틱에 갱신했다. 따라서 이 실행은 실제 오래된 자료를 주입한 신선도 검사나 실제 500ms 스케줄러 정지 시험이 아니다.

코어 계산은 원형 전체 클래스를 그대로 사용했다. 실제 MPC solver module은 `acados.acados_template.acados_ocp_solver_pyx`이며 C/Cython/acados 스냅샷에서 실행됐다. LongControl은 원형 Python이다. 입력 `SchemaInputs.touch`만 감싸서 실제 Cap'n Proto 필드를 명시적으로 배치했고, LongControl wrapper는 원형 반환값을 그대로 돌려주며 전후 상태와 출력만 기록했다. Toyota Python CAN 생성/디코딩, 실제 Panda C 권한 판단 및 실물 송신은 이번 검사에서 실행하지 않았다.

## 원형 소스와 원인

`signal_assist_runtime.py:77`은 서비스의 seen/valid/alive/수신 나이를 context 유효성에 사용하고, `:79`는 `feature enabled AND sd.enabled AND cc.longActive`를 context 활성 여부로 만든다. 첫 CC-only off 표본은 sd.enabled=True, CC.enabled=True, longActive=False, runtime valid=True였지만 runtime enabled=False였다.

`signal_start_guard.py:144-148`에서 enabled=False는 `reset()`을 호출한다. `:66-76`의 reset은 hold, session, box, frame/timestamp, pending/count를 지운다. 첫 off 표본은 hold=False, reason=disabled, box/session=None이었다. `:161-163`의 valid=False는 hold를 보존한다. 비교 조건은 실제로 그 차이를 확인했다.

같은 빨강이 다시 들어와도 `:133-136`의 fresh red 확인 규칙에 따라 150ms가 필요했다. 정지 기억이 사라진 뒤 초록은 빨강 anchor 없이 선택 권한을 확보하지 못했다. 최종 초록 표본에서도 pending=unknown, box=None, released=False였다. 따라서 이번 초록 후 출발은 “700ms 확인으로 기존 red veto를 정식 해제”한 경로가 아니라, 비활성 때 이미 veto가 reset되어 원형 모델 진행 의도가 남은 경로다.

`carrot_functions.py:533-542`는 실제 runtime context를 StartGuard에 전달하고, `longitudinal_planner.py:414-420`은 hold가 있을 때만 최종 정지 veto를 적용한다. 이 부분 체인에서 CC-only off→fresh 복귀가 순환적으로 정지 기억을 잃는 상태 전이를 직접 확인한 것이다. 전체 Controls/StateMachine/card/Panda 체인의 자동 복귀를 증명한 것은 아니다.
