# 레이더·당근 처리의 차량 속도 기준 대조

실제 로그를 기존 오프라인 어댑터로 다시 읽어 객체369표본과 measured snapshot405표본을 관찰했다. **레이더 입력의 지면 기준 속도와 당근 snapshot이 다시 계산한 속도가 최대 약0.37m/s 달랐다.** 실물 속도 정답이 없고 실제 제어도 비활성이므로, 이 차이를 센서 결함이나 실차 제동 실패의 확정 원인으로 해석하지 않는다.

## 같은 이름의 속도라도 계산 기준이 다름

- 원형 ARS510 fused는 bus0 SPEED(0xB4)를 차량속도로 사용한다. 객체 지면 속도에는 원형 프로파일의0.149/0.15 배율이 적용된다. `vRel = fused_ground_speed - B4_speed`다.
- Toyota CarState.vEgo는 네 바퀴 속도의 평균을 속도 필터에 넣어 만든 값이다. 동일 메시지의 B4 속도를 그대로 복사한 값이 아니다.
- MyTrack은 전달받은 point.vLead를 사용해 가속도를 계산한다.
- 기존 당근 measured snapshot은 point.vLead를 복사하지 않고 `v_lead = CarState.vEgo + point.vRel`로 다시 계산한다.

따라서 두 단계의 속도 차이에는 차량속도 기준, 필터 응답, 서로 다른 표본 시각이 섞인다. 일정한 한 배율을 더 적용하면 해결된다고 판단할 근거가 없다. 원형 프로파일·차량 인터페이스·당근 코어를 바꾸지 않았다.

같은 헤더 기준 비교는 각 CarState 헤더보다 늦지 않은 가장최근 B4를 사용하고100ms 이내만 집계했다. 이100ms는 진단 조건이며 제어 정책이나 타임아웃을 바꾼 값이 아니다. 첫5초는 첫CarState 헤더부터의 상대구간이다. log_2 전체의−3.2611m/s 최대 음수 차이는 초기5초에만 있으며 이후 결과와 구분한다.

속도 절댓값0.3m/s 기준의 분류가 두 계산 사이에서 달라진 것은 log_1의3표본이다. 이는 실제 제어 코드의 완전한 정지 판정을 대체한 검사가 아니다. 제공 객체에는 거리0~0.5m·중앙±0.5m·차량속도0.5m/s 이하의 근거리 유지 형상 조건을 만족한 표본이0개다. 이 자료로 근거리 보강의 실패나 성공을 입증하지 않는다. 최종L1 선택 변화·차량 제동 영향도 이검사에서는 측정하지 않았다.

B46,594프레임은 원형 helper로 길이8과 숫자 디코딩을 확인했다. **그 helper에 별도 체크섬 검증은 없으므로 이결과를 B4체크섬 통과라고 부르지 않는다.** PCM 체크섬 검사나 원본 객체 CRC 검사와 다른 범위다.

## 시각·기록 순서의 한계

기존 재생 경로와같이 로그 저장 순서를 사용하면 모델 헤더보다 이미 읽은 최신CarState 헤더가 새로울 수 있다. 모델 시점 measured snapshot405표본 중 음수 헤더 차이는 log_1/2에서각58개였다. 이현상은 서로 다른 서비스의 게시·기록 순서와 실제앱 수신 순서가 같다는 보장이 없음을 보여준다. 로그 전체의 헤더가 뒤로가는횟수를 센것을 ECU CAN 시각 역행이나 제어 프로그램 결함으로 해석하지 않는다.

원형 record는106프레임을 조립한다. record의시작시각, 끝프레임 수신시각, 그동안 갱신된 B4, 모델의촬영EOF가 서로다르다. `point.vLead - point.vRel`과 완료후의 최신B4를 뺀 잔차도 시간대조이며 디코딩오류 판정이아니다. 기록순서를무조건정렬해 실물수신순서인것처럼 만들거나, 새측정시각을 생성하지 않았다.

별도의 독립 메모리 관찰에서는 실제 decoder가 사용한 B4를 원형 반환값 변경 없이 확인했다. 2,433개 완성 record 모두 사용 B4가 record시작 뒤·완료 앞 또는 같은시각이었다. 그 사용값으로 계산한 `(v_ground - vRel) - used_B4` 잔차는 최대약8.9×10⁻¹⁶m/s였다. 프로브가 CAN packet의B4를 먼저읽은17point에서는 실제decoder가사용한값과 '최신B4'가 달라 최대0.038889m/s 잔차가 생겼다. 이것을 레이더 수치 오류로 판단하는 설명은 반박됐다. record 조립시간의중앙값은31.2/39.5/39.8ms였다. 독립 검토 세부사항은 `REVIEW_KO.md`에 보존한다.

## 실행과 다음 확인

최종 관찰 도구 SHA256은 `f6a363d9b75a1319c6f5efd53e980280c9c10ab162dd2681e50cd6eb714ae890`다. 실행은 exit0, 소스5파일지문 전후동일, CarParams전후동일, 실제차량송신0, 실제longActiveTrue0이었다. NumPy 집계와 기존 Python CAN/ARS·MyTrack·snapshot 계산을 사용했다. MPC·안전C·실물CAN송신을 이검사에서 실행한 것으로 보고하지 않는다.

원본 로그가있는 격리 작업환경에서 다음과같이 실행한다.

```bash
python speed_reference_probe.py --source-dir "$LAB_SOURCE" --logs-dir "$LOCAL_LOGS" --output-dir "$RESULT_DIR"
```

필요한 Python패키지·스키마는 기존 오프라인 검증환경을사용한다. 운영설정이나제어활성화는하지않는다. 다음에는 같은시각의 원본B4·바퀴속도·CarState필터·객체record·모델획득시각을 함께 비교해야하며, 바퀴미끄럼·타이어보정·실물거리/속도정답은 별도자료가 필요하다. 속도기준 차이 하나로 전체 급감속 문제를 설명하거나 임의보정을 적용하지 않는다.
