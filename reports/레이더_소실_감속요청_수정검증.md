# 레이더 소실과 감속 요청 전달 수정 — r10

RAV4 2022의 직접 종방향 제어에서 **오류 해제 대기 중 감속 목표가 덮이는 소프트웨어 결함을 재현하고 수정했다.** 실제 차량에서는 확인하지 않았다. 정상 빈 트랙, 레이더 오류, 근거리 선행차 선택 해제는 서로 다른 원인이다.

## 새로 확인한 원본 로그

기록 당시 스키마로 원본 네 파일을 직접 읽었다. 세 파일에 radarState 2,792개가 있었고, valid=True 2,672개·False 120개였다. 해당 메시지의 오류 플래그는 모두 False였다. 선택된 leadOne 1,630개는 모두 radar=False였고 leadTwo는 모두 미선택이었다. carControl 15,358개는 enabled/longActive가 전부 False였다. 나머지 파일에는 이 메시지들이 없었다.

이는 기록된 비전 기반 선택의 증거다. 오류 플래그 없음은 실제 레이더 사용·감속·안전의 증거가 아니다. ARS 오프라인 진단 재생의 175회 레이더 선택과 원본 상태를 합산하지 않는다. 스키마 두 파일 지문과 원본 파일 크기·수정 시각은 실행 전후 같았으며, 식별정보·좌표·운영 설정은 읽지 않았다.

## 재현된 원인과 수정

SelfdriveD는 invalid radarState를 오류 종류에 따라 처리한다. canError는 즉시 해제한다. 임시 불가·radarFault·wrongConfig·일반 통신 오류는 명목 3초 softDisabling을 거친다. 이 대기 중 host는 longActive를 유지하면서 Controls.forceDecel을 계획기로 보낸다.

원형 LongitudinalPlanner는 forceDecel이면 MPC에 목표 0m/s를 전달했다. 그러나 MPC의 ACC 경로가 다시 carrot.v_cruise로 대입했다. 정상 PCM으로 활성화한 합성 입력의 임시 오류·생산 중단 조건 각각 **고유 계획 호출 60회**에서 입력 0→실제 지역변수 21.3889m/s(77km/h)를 관측했다. 100Hz 행의 300회 반복 관측을 300개 계획으로 세지 않는다. 같은 3초 동안 양수 제어·CAN 명령이 지속됐다.

MPC에 기본 False인 force_slow_decel 인자를 추가해 당근 목표를 읽은 뒤에도 감속 목표를 유지했다. 호출자는 기존 actuator_accel_limits가 있는 정확 Toyota/RAV4 TSS2 2022·직접 종방향 제어에만 이를 전달한다. radarUnavailable=True는 유지한다. 모드 0 시험을 사용했지만 수정 조건 자체는 PCM 모드 0이나 레이더 오류에만 한정되지 않는다. 기존 forceDecel 출처인 운전자 주의 경고에도 같은 전달이 적용된다.

수정 파일은 longitudinal_planner.py·longitudinal_mpc_lib/long_mpc.py와 새 자동 검사 test_force_decel.py이다. 새 09_force_decel.patch는 기존 r9의 01~08 패치 뒤에 적용한다. 전체 변경 소스는 64개, 패치는 9개다.

## 직접 실행 결과

모든 시간은 고정 ego 15m/s·가상 100Hz 입력의 메모리 시험이다. 실제 차량 운동, 벽시계 100Hz 마감, USB/MCU 실행 시간은 포함하지 않는다.

| 입력 조건 | 기존 결과 | 수정 결과 | 해제 시점 |
|---|---|---|---|
| 건강한 빈 lead | 양수 CAN 133개 | 같은 결과 | 4초 내 해제 없음 |
| 오류 True·valid True | 양수 CAN 133개 | 같은 결과 | 정상 producer 계약과 모순되는 합성 입력 |
| invalid·canError | 즉시 해제, 양수 CAN 0 | 같은 결과 | 0.00초 |
| 임시 불가·fault·wrongConfig·invalid 무오류, 각각 | 3초간 양수 제어 300틱·양수 CAN 100개 | 양수 제어 5틱 뒤 음수 295틱; 양수 CAN 11·음수 89 | 3.00초 유지 |
| radarState 생산 중단 | 0.45초에 해제 대기, 양수 CAN 115개 | 양수 CAN 28·음수 87 | 3.45초 유지 |

주 에이전트는 원형 대표 4조건을 직접 재현했고 감속 전달 검사 2조건이 실패했다. 수정 후보 전체 8조건 후, 실제 수정 Planner 파일과 새 동결 MPC Python 사본을 명시적으로 로드해 8조건을 다시 확인했다. 마지막 실행의 구조 검사 80개와 별도 감속·해제 시점 10판정이 통과했다. 이 80개는 감속 성공만을 검사하는 항목들이 아니며, 원형 80·추가 관측 40·독립 재현을 고유 검사 수로 합산하지 않는다.

임시 불가의 별도 생성 CAN 기록에서는 첫 음수 제어가 요청 후 0.05초, 첫 음수 CAN이 0.34초에 나타났고 C가 허용했다. 정규 CAN 간격은 가상 시간 30ms였다. **수정 후에도 초기 양수 CAN이 남았다. 즉각 비양수 송신이나 급제동 성공을 보장하지 않는다.**

1초 오류 후 회복과 3.2초 오류 후 PCM 재활성의 두 조건·18판정도 직접 통과했다. 짧은 오류는 enabled를 유지하며 forceDecel이 해제되고 정상 목표로 돌아갔다. 해제까지 간 경우 정상 데이터만으로 재활성되지 않았으며 정상 PCM off/on 후 활성화됐다. 실제 정지·재출발 시험은 아니다.

실제 native MPC 회귀 79개가 통과했다(새 감속 검사 5개+기존 관련 74개, 5.40초). 타 Toyota 3종·2022 순정 종방향의 목표와 가속도 배열은 기존 경로를 보존했다. 다른 차량의 forceDecel 동작을 이번 수정으로 고쳤다고 해석하지 않는다. 카메라·신호 회귀 94개도 12.64초에 통과했으며 기존 NumPy 배열 shape 경고 15,826개를 별도로 기록했다.

## 실행 파일과 최초 실패 구분

수치 방정식·차원·solver ABI는 바뀌지 않았다. 기존 native 바이너리 6개를 새 경로로 복사했고 원본·사본 지문이 일치했다. 기존 .so를 덮거나 새 C 빌드를 했다는 결과가 아니다. 실제 수정 Python 파일·Cython 경로를 확인하고, 마지막 실행에서 MPC Python+native 6개 지문 및 Planner·안전 C 지문을 각각 실행 전후 확인했다. 전체 프로세스의 메모리 페이지나 모든 의존 모듈 동일성을 검사한 것은 아니다.

최초 최종 시험 준비는 이미 로드된 download clone의 패키지 경로 때문에 Planner 파일 경로 검사에서 실패했다. 그때는 사례 실행 0이었다. main Planner를 정식 모듈명으로 명시 로드해 수정했다. pytest 최초 준비도 전체 프로젝트 conftest의 미빌드 params_pyx로 수집 전에 실패했고, 격리된 native 검사 설정으로 관련 시험을 실행했다. 두 최초 준비 실패를 보존했으며 CAN·제동 실패로 세지 않는다.

## 남은 문제

보존된 근거리 모의시험은 약 0.49m의 점이 남았는데 선행차 선택이 풀렸고 정지 요청도 해제됐다. 이는 shouldStop 유지 중 잔여 양수 문제와 다르다. 당시 코드 지문이 완전하지 않아 현재 소스를 당시 버전으로 소급하지 않는다. 건강한 빈 lead에 forceDecel이 없으면 이번 수정은 개입하지 않는다. 근거리 기능은 현재 CP.radarUnavailable=True에서 꺼져 있다. 실물 근거 없이 이 플래그·필터·거리 문턱을 바꾸지 않았다.

실제 ECU 모델/FW, 활성 종방향 CAN·모델·계획·상태와 동기화된 영상, 실제 레이더 발행 시각과 시간 기준, Konik ARM 전체 빌드·처리 마감, PCS/AEB 보존, 회생·CAN 필터 효과는 여전히 추가 자료와 별도 검증이 필요하다. 기존 모의 접촉과 실시간 마감 실패 기록도 유지한다. 실차 배포 허용은 False이며, 사용자 중단 전 지속 검증을 계속한다.

## 파일 준비

고정 r10을 별도 빈 폴더에 준비한다. 이전 r9·태그는 보존한다.

```sh
git clone --branch lab-20261013-r10 --depth 1 https://github.com/Mlnege/rav4-ars510-validation.git
cd rav4-ars510-validation
bash tools/remote_download.sh --destination /data/rav4-validation-lab-r10 --install-deps
```

이 명령은 기준 소스·순차 패치·변경 파일 지문·CPU/Python 조건을 검사하고 격리된 파일과 의존성을 준비한다. 차량 설치·Params·Panda·PCS/AEB·제어 활성화는 변경하지 않는다. r10 게시와 실제 다운로드 확인은 배포 검증 문서에 별도로 기록한다.
