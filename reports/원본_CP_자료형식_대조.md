# 원본 CarParams의 현재 자료 형식 대조

원본 CP 5개를 현재 cereal 자료 형식으로 읽었을 때, 확인한 제어 필드16개와 안전 설정·펌웨어 항목 수는 모두 같았다. 새로운 통합 검사에서 원본 CP를 쓰기 위한 기본 확인이며 전체 필드·전체 자료 형식·생성자·설치 펌웨어 호환성을 입증한 결과는 아니다.

| 원본 | CP 표본 수 | 직접 롱컨 설정 | 안전 값 | 현재 형식과의 검사 차이 |
|---|---:|---|---:|---:|
| log_a | 1 | True | 73 | 0 |
| log_b | 2 | False | 585 | 0 |
| log_c | 0 | 자료 부족 | — | 검사하지 않음 |
| log_d | 2 | True | 73 | 0 |

필드는 차량의 정적 모델명·flags·직접 롱컨·pcmCruise·radarUnavailable·alternativeExperience·질량·축간거리·무게중심·조향비·레이더 지연·롱컨 지연·DSU·BSM·최소 속도2종이다. VIN·serial·펌웨어 문자열은 읽거나 출력하지 않았다. carFw는 개수만 확인했고 원본5개 모두0이었다.

첫 도구 실행은 exit0이었다. 별도 점검 버전에 자료 형식/부트스트랩4파일 지문과 원본4파일의 크기·수정시각 확인을 추가한 뒤 다시 직접 실행했다. 두 실행의 제어 표본이 같고, 마지막 실행의 source 지문·원본 파일 상태도 같았다. 마지막 버전은 Ruff 검사도 통과했다. 최초 도구의 import 정렬 지적은 준비 코드 정리 문제였으며 데이터 해독 실패가 아니다. 이전 도구와 결과는 덮어쓰지 않았다.

이 자료의 Bool 설정이 실제 제어 활성화를 뜻하지 않는다. 원본 로그의 longActive는 모두False였으며, Card 생성자가 메모리 설정에 따라 바꾸는 필드와 CS.radarInput을 새로 쓰는 동작은 다음 통합 검사에서 별도로 추적한다. 기존 factory CP73을 원본 log_b의585 대신 사용하지 않는다. 운영 Params와 차량·Panda에는 접근하거나 송신하지 않았다.

시간 출처도 따로 확인하고 있다. Linux의 MONOTONIC과 BOOTTIME은 절전 시간 포함 방식이 달라 같은 시간 축으로 일반화할 수 없다. 이번 차량의 실제 기록 backend와 절전 이력은 미확인이다. [Linux 공식 시간 문서](https://www.kernel.org/doc/html/latest/core-api/timekeeping.html)
