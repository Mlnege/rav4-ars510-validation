# 기록 Panda 설정과 오프라인 안전 검사 비교

실제 기록과 현재 코드의 모의 안전 검사는 같은 실행이 아니다. 원본을 직접 읽어 CP 설정·Panda 설정·오류를 확인했고, 새로운 실제 CAN→호스트 시험의 C 결과와 구분했다. 설정이나 펌웨어는 변경하지 않았다.

| 익명 로그 | CP 표본 수 | 직접 롱컨 설정 | CP/Panda Toyota 안전 값 | 순정 롱컨 비트 |
|---|---:|---|---:|---|
| log_a | 1 | True | 73 | False |
| log_b | 2 | False | 585 | True |
| log_c | 0 | 자료 없음 | 자료 없음 | 자료 없음 |
| log_d | 2 | True | 73 | False |

현재 소스의 순정 롱컨 비트는 `ToyotaSafetyFlags.STOCK_LONGITUDINAL = 2 << 8`, 즉512다. 585는73에 이 비트가 추가된 값이다. 원본 CP의 직접 롱컨 설정은 True3개/False2개이며, 다섯 CP를 모두 직접 롱컨 True로 요약하면 틀리다. pcmCruise/radarUnavailable은 모두True, alternativeExperience는 모두1이다. 직접 롱컨 True 설정도 실제 활성화와는 다르며, 원본 CarControl 15,358개는 longActive=False였다.

원본 Panda 상태는 총1,484개다. 초기 elm327 모드202개와 Toyota 모드1,282개를 따로 읽었다. Toyota 모드는 log_a73/264표본, log_b585/505표본, log_d73/513표본이다. 모든 Panda 상태의 controlsAllowed=True는0, safetyRxChecksInvalid=True는0이고 오류 목록 표본도 없었다. firmwareSignature·serial·VIN 등 식별 필드는 읽거나 출력하지 않았다. 이 관찰은 설치 펌웨어 코드나 실물 릴레이의 동작 검증이 아니다.

새 호스트 시험은 세 로그 모두 수동 RAV4 2022·alpha_long=True인 factory CP를 선언했다. 원형 Card 생성자까지 거친 별도 설정 표본은 Toyota model2/안전 값73/alternativeExperience1/flags1372이며, C에 전달한 값도(2,73)/alt1이었다. 따라서 log_b의 안전 값585와 같은 시험이 아니다. 코드가 만들어 낸 CP 설정 표본과 실제 기록 CP를 구분한다.

그 모의 C는 원본 순정 CAN 전체를 받았을 때 릴레이 충돌을 감지하고 생성 명령26,302개를 모두 거부했다. 기록 Panda의 오류 목록이 비어 있다는 사실과 이 결과를 합쳐 실물 릴레이 고장으로 확정할 수 없다. 설치 펌웨어·수신 경계·하드웨어·초기화 차이는 아직 검증 대상이다. 충돌 메시지를 지우거나 C 제한을 풀어 통과시키지 않았다.

추가로 세 번째 도구를 직접 실행해 순정 명령과 안전 모드 전환의 상대시각을 대조했다. bus0의 조향 명령0x2e4는 log_a297/log_b376/log_d334개 모두 최초 기록 Toyota 모드 전에만 나타났다. 마지막 조향 명령도 그 모드 표본보다121~136ms 앞이었다. 저장순서의 직전 모드 역시 elm327 또는 아직 관측되지 않은 상태였다. 직접 롱컨 기록인 log_a의0x343213개와 log_d의223개도 전환 전에만 나타났다. log_b의0x3432055개 중1801개는 최초 Toyota 표본 이후였지만, 이 기록의 안전 값585는 순정 롱컨 비트를 갖고 있었다. 헤더 시각 기준과 저장순서 기준의 경계 표본1개 차이를 구분했다.

따라서 시작부터 Toyota73을 고정한 모의 검사와 실제 기록의 초기 elm327→Toyota 전환을 같게 취급하면 안 된다. 이 상대시각 결과는 기록의 빈 오류 목록과 모의 릴레이 차단을 설명하는 구체적인 초기화 차이다. 실제 모드 전환 순간·설치 펌웨어·하드웨어 작동의 증명은 아니다. 다음 검사는 원본 모드 전환을 메모리 C에 순서대로 적용하며, 원본 CAN 삭제나 릴레이 강제 해제 없이 원형 정책으로 관찰한다.

후속 C-only 진단을 완료했다. 기록된 모드 전환을 정식 설정 함수로 적용하고, 물리 수신과 송신 반환·거부 통지를 원형 프로토콜대로 구분했다. 3로그×1초 주기 위상2개의6실행·60검사가 통과했고 기록CS15,401개에서 relay·controls·long·RX-invalid True는0이었다. 물리RX647,115개는 C RX hook에서1을 반환했다. 반환191,166개/거부34개는 수량과 원형 의미를 보존하되 수신으로 재주입하지 않았다. 처음에 통지를 모두 RX로 넣어 실패한6개 판정과 그 코드도 보존했다. root도 log_b/위상0을 지문 동일 복사본으로 직접 재실행해6,022표본·실패0·소스/라이브러리 불변을 확인했다. 이 새 검사에는 이전의 생성 CAN26,302개 TX 재검사나 차량 송신이 없다.

두 새 읽기 도구를 각각 직접 실행해 exit0을 확인했다. 첫 도구는 Panda 설정·권한·오류만 읽었고, 두 번째는 CP의 직접 롱컨과 순정 롱컨 안전 비트를 추가로 대조했다. 첫 결과를 덮어쓰지 않았다. 실제 CAN→호스트의 대표 log_a도 독립 복사본으로 재실행해12검사 통과·23개 결과군 불일치0·레이더 입력175회·생성/C거부5,624개를 확인했다. 이는 활성 제어·실차 급제동·회생·PCS/AEB의 성공 증거가 아니다.
