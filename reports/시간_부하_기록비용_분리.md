원형 코어·기존 장시간 worker·native 바이너리를 변경하지 않고 새 작업 도구에서 40조건과 4개 비용 비교를 직접 실행했다. exit0, 213,298단계 호출, 선택 소스/native 지문 불변, CP 불변, 메모리 CAN checksum/범위 오류0을 확인했다. 데이터와 센서는 합성이며 전체 앱 권한·실물 송신·카메라 인식·PCS/AEB 안전성 검사와 다르다.

고정 실행 파일은 `diagnostic_timing_run06.py`, SHA256은 `5d1fb3fd57022d690fa5428ac7f62410e0572f2167617c82631d81e68fca8f0c`이다. 결과 `diagnostic_run_06_csv_equivalent/diagnostic_results.json`의 SHA256은 `ad11f3eb8f378d59a7e3c9fc5a87c094dba1fd6c0c32ad00826bc663da5a4e6a`이다. 실행 파일 지문은 결과에 기록한 지문과 직접 일치했다. 결과 작성 시각은 2026-10-12 19:15:25.599928 KST이다. 비용 비교 4군의 실제 측정 시간 합계는 288.008908초이며 각 군은 약72초였다. 프로세스 시작~종료 전체 벽시계는 이 버전에서 따로 저장하지 않았으므로 정확한 전체 실행시간으로 대체하지 않는다.

## 같게 맞춘 비교 조건

각 군은1440계획·7200제어 호출이다. 기록군은 이전35분의 기록 구조처럼 계획1행+제어5행 CSV, 명목60초마다 flush를 사용한다. 평균 행 수만 맞춘 것이 아니라 기존 제어 열19개와 계획 결과 열을 사용했다. 입력은 비용 비교용 고정 합성 vEgo15m/s·aEgo0으로 두어 차량 운동 때문에 계산 분기가 달라지는 효과를 줄였다. 실제 원형 계산의 인자·반환값을 가짜 알고리즘으로 바꾸지 않았다.

매번 같은 SignalAssistMode2 준비 상태를 확인하고 비용 비교를 시작한다. 재생성군은12초마다 새 객체를 만들며 같은 준비 상태를 위해 추가100계획 warmup을 실행한다. 이 추가 warmup은 측정 phase로 분리했고 이전35분에는 없던 비교용 부하다. 따라서 재생성군의 큰 호출 간격을 이전 worker의 초기화 비용이나 MPC 비용이라고 이름 붙이면 안 된다.

## 최대 호출 간격의 구간 확인

저장한 `stage_trace.jsonl`에서 실제 LongControl 호출 시각으로 가장 긴 구간을 다시 찾았다. 이 시각은 pacer의 앞 시각과 몇 μs 차이가 있으므로 표의 최소/최대 수치와 동일한 타임스탬프라고 가정하지 않는다. `gap_analysis.json`은 새 파생 결과다.

| 재생성군 최대 gap | 마지막/다음 계획 step | 재생성 함수 호출 | 추가 warmup의 처음~마지막 계측 범위 |
|---|---:|---:|---:|
| 기록 없음158.573111ms | 959→960 | setup3.312129ms, CAN setup0.055866ms | 142.804675ms |
| CSV156.962117ms | 479→480 | setup1.098063ms, CAN setup0.050606ms | 143.171454ms |

이 새 실험의 큰 gap에는 같은 준비 상태를 맞추기 위해 넣은 추가 warmup이 들어 있다. 각 범위는 함수의 시작/끝 경계이고 중첩 단계 비용을 전부 더한 값이 아니다. 이를 근거로 이전35분의322.9ms 지연을 warmup 때문이라고 확정하지 않는다. 이전 worker에는 같은 추가 warmup이 없었다.

다른 담당자의 독립 읽기 검토도 같은 구간을 확인했다. 기록 없는959→960 사이의 추가100계획에서 planner_total 합계87.324ms, 그 안의 중첩 MPC40.908ms, 추가500 LongControl9.959ms가 있었다. 기록 있는479→480에서는 추가100계획의 planner_total 합계88.157ms였다. 이를 새 테스트 실행 결과로 합산하지 않으며, MPC를 planner에 다시 더하지 않는다. 비용 비교는 군당1회의72초 표본이므로 OS·환경 잡음과 추가 준비 경로 차이의 불확실성이 남는다.

## 계산과 기록 비용

warmup을 제외한 paced 비용의 직접 관측은 MPC p99 0.750155ms/최대2.134837ms, 전체 planner p99 1.673918ms/최대23.169004ms였다. MPC·신호 runtime은 planner 안에 중첩되므로 합산하면 이중 계산이다. 객체 재생성 함수10번의 최대는3.415310ms였다.

계획 CSV write 최대0.960186ms, 제어 CSV write 최대0.954637ms, 계획/control flush 최대0.709160/0.549326ms였다. 이 표본에서는 기록을 켠 재사용군의 최대 간격이13.85→16.27ms였으나 다른 시간대의 OS·파일시스템 상황까지 동일하다는 증거는 없다. 기록 비용이 이전322ms 전체의 원인이라고 단정할 수 없다.

## sleep과 실제 CPU 소비

40조건은 기존5종 시간/자료 상태 각각50/150/323/600ms에 실제 sleep과 별도 CPU-work를 주입했다. CPU-work는 원형 모델의 가짜 반환값이 아니라 thread CPU 시간을 실제로 소비하는 별도 부하다. 과거 지연의 발생 원인과 동일하다고 주장하지 않는다.

앞선 smoke에서 sleep20조건은 wall5617.209ms/CPU0.705ms, CPU-work20조건은 wall5618.185ms/CPU5615.067ms로 분리됐다. 두323ms 부하 모두 frozen clock에서는 논리 시간이0만큼 진행했고 관측 나이140ms를 유지했다. 실제 경과 IO 시계에서는 원형 자료/헤더를 보존해 나이가 진행한다. 오래된 모델 body에 새 헤더를 붙이는 사례는 별도 이름과 획득 시각을 보존하므로 신선한 자료 성공으로 부르지 않는다.

`cc_active_full_app=null`이다. source enabled에서 구한 단독 fixture 활성 조건과 실제 앱의 이벤트/soft-disable/card/Panda 권한을 혼동하지 않는다. 별도 담당자의 전체 원형 활성 체인 검증과 결합한 뒤 코어 수정 필요성을 판단한다.

고정10ms 차량 모형과 실제 wall 경과를10ms 소구간으로 적분한 모형은 별도 값이다. 실제 가정 지연150ms·잔여 미적분 시간도 기록한다. 이 값으로 현장 소음·렌즈/보정·색 정확도·회생/마찰·순정 AEB 유지나 제동 성능을 입증하지 않는다. 이전322.9ms 실제 원인은 계속 미확정이다.
