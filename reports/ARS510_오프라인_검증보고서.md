# RAV4 Hybrid 2022 ARS510 오프라인 호환 검증

2026-10-12, 한국 출고 차량의 첨부 `dad.zip` 분석 결과.

## 결론과 완료 범위

실제 첨부 CAN에서 ARS510의 객체·메타데이터 레코드 형식과 CRC, 슬롯 구조를 확인했다. 원형 `fused` 디코더가 생성한 객체를 최신 CarrotPilot의 실제 객체 후처리, `liveTracks` 직렬화, 선행차 선택 코어, `radarState` 직렬화까지 오프라인으로 연결했다.

완전한 객체 레코드 2,433개와 메타데이터 레코드 2,436개 모두 CRC 검사에 통과했다. 객체 슬롯의 거리·횡거리·지면 기준 속도는 별도 DBC 구현으로 2,878개 표본을 대조하여 불일치가 없었다. `fused` 출력은 369개 객체 표본이며, 기록된 비전 모델과 함께 실행한 선행차 선택은 레이더 기반 175회, 비전 전용 비교는 0회였다.

확인한 것은 **첨부 CAN의 ARS510 프로토콜 형식 호환성과 오프라인 처리 경로**다. ECU 실물·펌웨어 출처, 거리의 실제 정답, 한국 차량 전체 호환성, PCS/AEB 유지, 실차 제어 안전성은 확정하지 않았다. `carFw`가 비어 있어 “실물 ARS510에서 발생한 것으로 독립 확인”하는 성공 기준은 아직 충족하지 못한다.

따라서 레이더 패치는 오프라인 전용이다. `CarInterface`에 등록하거나 `radarUnavailable`을 변경하지 않는다. 실차 설치·CAN 송신·Panda 변경·레이더 비활성화 요청을 실행하지 않았다.

## 소스 구조와 지원 범위

ARS510 저장소의 `ars510/`는 프레임 조립, CRC, 20개 객체 슬롯, 객체 수명, 속도 필터를 처리하는 표준 Python 코드다. `openpilot/`는 설치·인터페이스 후킹, `upstream/`은 단일 파일 제안과 ACC DBC, `dbc/`는 원시 버스 및 Cabana 가상 객체 DBC, `tools/`는 재생·진단, `tests/`와 `data/sample/`는 검사·공개 샘플을 제공한다.

레포 자체 자료는 RAV4 2022의 `8821F0R01100`·`8821F0R03100`, RAV4 2023–25의 `8821F0R03100`, C-HR의 `8821FF410200`–`8821FF410500`, Yaris의 `8821F0D04100`·`8821F0D05300`을 다룬다. Yaris는 0xB4가 없어 `acc` 프로파일로 제한한다. 이 레포의 과거 재생·도로 수치는 이번 차량의 검증 수치로 사용하지 않았다. 이번 어댑터는 검증 대상인 RAV4 TSS2 2022로만 제한한다.

## Vision Only의 원인

확인된 코드 조건은 다음과 같다.

1. RAV4 2022는 `RADAR_ACC` 차량이다. `ToyotaTSS2PlatformConfig.init()`은 이 그룹의 radar DBC를 맵에서 제외한다.
2. Toyota `CarInterface._get_params()`는 radar DBC 부재로 `radarUnavailable=True`를 설정한다.
3. 기존 `RadarInterface`는 이 플래그가 True이면 CAN 파서를 만들지 않는다. 기존 파서는 TSS2의 0x180–0x19F, TSS-P의 0x210–0x22F를 처리하며 ARS510의 분할 레코드를 처리하지 않는다.
4. 최신 `effective_radar_track_mode()`는 설정값을 Hyundai에 적용한다. Toyota의 `radarUnavailable=True`는 비전 전용 모드 -2로 선택된다. “Radar Track Mode 2” 선택만으로 Toyota용 객체 디코더가 생성되지 않는다.

첨부 CP의 `radarUnavailable=True`는 이 기본 구현과 일치한다. `carFw entries=0`은 이 DBC 조건의 직접 원인이 아니다. 수동 차량 선택 등은 펌웨어 조회를 건너뛸 수 있다. 이 사실만으로 ECU 고장을 판단하지 않았다.

최신 ARS510 설치기의 `detect()`는 CAN 0x80/0x85나 펌웨어를 검사하지 않고 플랫폼과 `RADAR_ACC`를 검사한다. CAN ID 기반 감지는 과거 패치에 있다. 일부 설치 문서의 설명과 최신 코드가 달라 실제 구현을 기준으로 판단했다. 초기 fingerprint가 끝난 뒤 객체 송신이 시작되는 경우도 레포에 문서화되어 있다.

장치에서 `fused`를 선택했는데 후킹이 왜 반영되지 않았는지는 설치 파일·재부팅 이력·실제 import 대상 자료가 없어 확정할 수 없다. 업데이트로 설치가 사라짐, 다른 체크아웃에 설치, 이전 감지 코드, 재시작 누락은 가능한 추가 확인 항목이다. 최신 소스에는 정확한 `Vision Only` UI 문자열이 없어 표시 화면의 장치 버전도 별도 확인이 필요하다.

## CAN ID와 신호

실제 수신 버스는 1이며 버스 번호를 바꾸는 패치는 필요하지 않았다. 숫자 130의 수신 출처 등은 버스 1과 합쳐 해석하지 않았다.

| 버스·ID | 용도 | 검증된 처리 또는 공개 정의 |
|---|---|---|
| 1 / 0x80 | 객체 목록 | `12 E4` 시작, 8바이트×106개. 매 프레임 byte1–7을 연결한 742바이트 레코드 |
| 1 / 0x85 | 메타데이터 | `10 90` 시작, 8바이트×21개, 147바이트. 객체 출력 자체에는 사용하지 않음 |
| 1 / 0x81, 0x86 | 레코드 marker | `30 00 00 00 00 00 00 00`; 객체 생성 입력으로 사용하지 않음 |
| 1 / 0x235 | ACC 속도·상태 | Motorola STATE 11\|4, REL_SPEED 31\|11 ×0.125−128 m/s, TARGET_ID 60\|5 |
| 1 / 0x237 | ACC 거리·횡거리 | Motorola LONG_DIST 11\|13 ×0.025 m, LAT_DIST 30\|12 ×0.01−20 m, PRESENT 50\|1 |
| 1 / 0x239 | ACC 식별·시각 | CLASS 11\|4, PRESENT 27\|1, IN_OBJECT_LIST 31\|1, TIMESTAMP 26\|32 µs |
| 1 / 0x23B | ACC 크기·검사값 | 3바이트, WIDTH 11\|12 cm, COUNTER 15\|4 |
| 0 / 0xB4 | 차량 속도 | byte5–6 BE16 ×0.01 km/h, 상대속도 계산에 필요 |
| 0 / 0x24 | 회전속도 | Toyota yaw rate, Motorola 1\|10, 0.244 deg/s·code−125 |
| 1 / 0x192, 0x194 | 선택 객체 요약 | 원형 fused에서는 summary 융합 비활성화 |

0x80의 CRC는 `zlib.crc32(record[1:737])`와 LE32 `record[737:741]`를 대조한다. 0x85는 `[1:141]` CRC와 `[141:145]`의 LE32를 대조한다.

객체는 record byte17부터 36바이트×20개이다. 아래 비트는 슬롯 기준 Intel 순서이다.

| 신호 | 비트 | 변환·의미 |
|---|---|---|
| 슬롯 번호 | 2\|6 | 자기 슬롯 0–19, 비할당 63 |
| 객체 age | 24\|7 | 레이더 주기 수, 126에서 포화. 슬롯과 age 연속성으로 중복되지 않는 처리 ID 생성 |
| 전방 거리 | 32\|12 | `(code−160)/16` m |
| 횡거리 | 44\|12 | `(code−2048)×0.015` m, 왼쪽 양수 |
| 지면 기준 전후속도 | 64\|10 | 공개 디코드·가상 DBC는 `(code−510.5)×0.15` m/s. 원형 fused는 보정 0.149 사용 |
| 속도 불확실성 | 240\|7 | 원형 fused의 가중치 입력 |
| 상대속도 | CAN 단일 신호 아님 | 필터된 지면 기준 속도−신선한 차량 속도 |

가상 DBC의 0x700+slot은 ECU가 보내는 주소가 아니다. 재조립한 슬롯을 가상 메시지로 보여주는 용도다. 이를 실 CAN 8바이트에 직접 적용하지 않았다. 전체 DBC 신호·비트·배율은 `dbc_signals.csv`에 제공한다. 횡거리·일부 속도 배율의 문서상 불확실성과 레이더 자체 속도 오차도 보존한다.

“표본”은 한 객체의 여러 시점 출력을 각각 센 값이다. ID 수는 파일별이며 다른 파일의 같은 ID를 한 실물 객체로 연결하지 않았다. lead 수는 leadOne/leadTwo 선택 인스턴스이며 정확도나 감속 성공률이 아니다.

슬롯 index·헤더 할당 수 불일치는 0이다. 0x235/0x237/0x239/0x23B는 합계 31,595개 프레임이 독립 DBC 디코딩에 성공했다. 숫자상 디코딩은 checksum 검증이나 실제 target 존재를 뜻하지 않는다. 0x235의 대부분은 STATE=1, 즉 idle이며 target-present STATE=5는 파일별 3/186/56개다.

정상 객체 레코드의 조립 시간은 약27.02–49.03ms, 기록 시작 주기는 약40.54–130.64ms였다. `rlog_12`의 약6.75초에는 106개 중 81개만 기록된 불완전 레코드 1건이 있었다. 순서 오류에서 이를 버리고 정상 931개를 보존했다. 이는 로그의 누락이며 ECU가 실제 송신을 누락했는지, 로깅·수신에서 빠졌는지는 구분하지 못한다.

원형 fused는 새 객체 age60 미만을 보류하고, 경로·거리·속도 불확실성을 검사한다. rlog_12의 raw 출력 692개 중 fused는 6개다. 필터를 완화하거나 객체를 새로 만들어 수를 늘리지 않았다. 정지 상태·기존 형상·경로 제외 등에 관한 정확한 실물 분류는 영상·정답 자료 없이 판단하지 않았다.

fused 거리 범위는 파일별 3.45–14.18m / 3.33–20.58m / 2.87–2.94m, 상대속도 범위는 −1.69–0.81 / −6.99–0.35 / −1.23–−1.06m/s이다. `dRel`, `yRel`, `vRel`, `vLead`, `aLead`, `jLead`의 비유한 출력은 0이다. 이 범위가 물리적 정답이라는 뜻은 아니다.

## 패치 구현과 검증

원형 `ars510/`를 MIT 라이선스와 함께 복사하고 별도 오프라인 어댑터를 추가했다. 원형 FUSED_CONFIG와 필드 정의를 수정하지 않았다.

- 106프레임의 길이·type·연속 번호·시각·최대 조립시간 0.15초를 검사한 뒤 원형 CRC 검사를 실행한다.
- 지원 속도·yaw·ACC 메시지에는 정확히 8바이트를 요구한다.
- 각 정상 객체 집합으로 `self.pts`를 교체하고 실제 `RadarInterfaceBase.update_carrot()`·`MyTrack`을 실행한다. `vLead`는 원형의 필터된 지면 기준 속도로 전달한다.
- 여러 레코드를 묶어 입력해도 모두 후처리한다. 동일 시각의 여러 완성 레코드는 측정 시각을 임의 생성하지 않고 거절한다. 차량 속도·가속도 이력은 외부 호출당 한 표본으로 유지한다.
- CRC·순서 오류, 0.5초 타임아웃에서 객체와 필터 이력을 비우고 오류를 전달한다. 정상 레코드 완성 후 회복한다.
- 처리 객체 번호는 1000 이상으로 분리하고 새 이력에서 재사용하지 않는다. 기존 코너 레이더의 예약 번호와 downstream signed 32비트 한계를 검사한다.
- 기본 생성자는 거절한다. `offline=True` 및 정확한 RAV4 2022·RADAR_ACC 조건이 필요하다. 차량별 live dispatcher는 변경하지 않는다.

오프라인 재생은 CAN의 원래 수신시각과 기록된 carState/modelV2/livePose를 사용한다. 실제 최신 cereal 스키마로 `liveTracks`를 직렬화·역직렬화하고 기존 `DPathRadarController`로 전달한다. 독립 수신 검증 인스턴스는 모드1, 비교 인스턴스는 모드−2를 명시한다. 원래 CP의 `radarUnavailable`·종방향·안전 설정은 전후 동일하다. 이는 현장 Radar Track Mode2 전체 기능 검증이 아니다.

Windows Python3.12.10과 Python CAN/동역학 백엔드에서 실행했다. Params 확장 모듈이 없는 데스크톱에서는 프로세스 안에서 Params 접근 자체가 실패하도록 막았다. 레이더 디코더·필터·스키마·선택 알고리즘을 대체하지 않았다. 소켓 프로세스, 전체 planner/가감속 계산기, Cython 성능 비교, Konik 장치용 전체 native build, Panda 펌웨어 빌드는 실행하지 않았다.

## PCS/AEB와 남은 확인 사항

현재 Toyota 소스는 RADAR_ACC의 실험적 직접 롱컨에서 `DISABLE_RADAR`를 설정하며, 초기화 때 ECU 0x750/subaddress0xF에 송신 중지 요청을 구성한다. stockAeb/stockFcw 읽기도 이 플래그에서 제외한다. ARS510 레포도 이 경로의 PCS/AEB 영향을 별도 문제로 다룬다. 버스1 객체가 남아 있다고 순정 안전 기능이 유지되는 것은 아니다.

또한 현재 CarrotPilot의 `safety.h` 가속도 검사에는 0이 아닌 요청에서 `controls_allowed=true`를 설정하고 기존 제어 허용 상태 검사식을 주석 처리한 코드가 있다. 설치된 Panda 펌웨어에서 동일 코드가 실행되는지는 확인하지 않았다. 이번 패치로 이 파일이나 검사 조건을 바꾸지 않았으며 “기존 Panda가 모두 보호한다”는 안전 보장도 하지 않는다.

필요한 추가 자료는 다음과 같다.

1. 순정 상태에서 확보한 실제 레이더 ECU 품번·펌웨어 식별. 이 작업에서 실차 진단 요청은 보내지 않았다.
2. 장치 소스 커밋, 설치한 ARS510 파일과 프로파일, 실제 import 경로, 설치 후 재시작 여부의 읽기 전용 확인.
3. 버스0·1·2의 CAN과 carState/modelV2/livePose/liveTracks/radarState/carControl/longitudinalPlan이 함께 있는 연속 로그. cold start의 송신 시작부터, 앞차 이동·정지·cut-in·oncoming·고속 원거리 상황을 포함할 것.
4. 별도 시설·절차에 따른 순정 PCS/AEB 유지 검증. 실제 제어 적용보다 먼저 해결할 조건이다.
5. 영상·동기화된 거리/속도 정답과 여러 차량·상황 자료. 현재 약159초의 자료만으로 필드 오차와 제어 정책을 검증할 수 없다.
