# ACC 관측 누락·오래된 관측의 단계별 원인

결론: 이 합성 시험에서는 큰 속도·거리 낙관이 **0x80 원본 해석 뒤 원형 fused 필터에서 먼저 발생**한다. MyTrack과 당근 레이더는 이 값을 이어받는다. MPC의 수렴용 거리 보정은 접촉 직전에야 나타나므로 최초 원인이 아니다. 원형 fused 설정은 모든 케이스에서 같다. full은 기존 설계의 ACC 추가 관측을 받지만 missing·idle·stale는 받지 않는다.

이 결과는 알려진 필드만 사용하는 합성 입력이며 실제 ECU 모델·센서 오차 분포가 아니다. 공개 슬롯의 속도 불확실성 코드47을 고정한 조건이다. ACC CHECK_BYTE는 미검증 placeholder0이고, 실제 차량 송신은0이다. 운영 설정·코어·root-owned runner/bridge를 수정하지 않았다.

## 읽은 실제 단계와 시각

`acc_contract_diagnosis.py`는 원형 `_payload`·`_fused_speed`를 호출하는 관찰 wrapper로 결과를 읽는다. 반환값은 그대로다. 같은 record의 합성 생성시각/기준값,0x80 raw 객체, 필터 상태, MyTrack 출력, DPath L1, 실제 native MPC의 관측/예측값과 생성된 ACC_CONTROL 명령을 기록했다. 원본 record가 완성 record와 바이트·순서로 맞는지도 확인한다.

기본 조건은 자차·앞차20m/s, 초기60m,7초부터 앞차−5m/s²다. 차 반응 가정은 명령 지연0.10초와1차 응답 시정수0.15초, 객체 주기0.06초,106프레임 조립 전송시간0.0315초다. 명목 active/유효 입력 조건이며 전체 controlsd 권한 검사의 대체가 아니다.

원형 assembler의 record 시각은 **첫 CAN 프레임 시각**이다. 실제 계산은 마지막 프레임이 도착한 뒤에 가능하다. 추가 sensor delay는 합성 생성시각과 첫 프레임 사이에 넣었다. DPath에 선언한 `CP.radarDelay`와 이 추가 지연을 혼동하지 않았다. JSON에는 생성시각, first-frame 시각, model 시각, 자료 나이를 따로 남겼다.

## 같은 설정에서 다른 결과가 생기는 이유

`ars510/interface.py:417`의 원형 white-noise fused 속도 필터는 속도 불확실성 코드로 측정 가중치를 정한다. 여기서는 코드47×0.045=σ2.115m/s, 분산4.473225다. 원형 과정 잡음은 가속도 표준편차1.5m/s²와 record 간격0.06초로 계산된다. missing의 object Kalman gain은7.08초 약0.04350이며, 새 raw 속도 차이의 약4.35%만 한 번에 반영한다.

full은 같은 object σ/age/config을 쓰되, 위치·가용성·시각으로 연결된 ACC 대상의 `vRel+vEgo`를 σ0.13m/s의 추가 관측1개로 넣는다(`interface.py:571`). 여기에 맞춰 상태 분산도 낮아진다. full의 object gain이 더 작더라도 ACC 관측으로 다시 보정되므로 감속을 더 빨리 반영한다. full도 원형 innovation 제한·필터 때문에 지연이 있으며 완벽한 센서와 같지는 않다.

`interface.py:336`은0x235/0x237 양쪽을 갖고0.1초 이내이며 같은 native 물체와 일치할 때 ACC association을 유지한다. missing은 처음부터없고 idle는가용성False로 둘 다 지워지며, stale는 마지막 유효 관측이0.1초를 넘으면 association을 해제한다. 어느 경우든 추가 관측0개로 돌아간다.

`interface.py:488`의 거리 필터는 filtered vRel로 예측한 다음 거리 측정 쪽으로 gain0.1만큼 보정한다. 속도를 높게 추정하면 닫히는 속도를 작게 추정하여 거리도 더 길게 남긴다. full은 연결된 ACC의 거리도 기존 acc_range=True에 따라 사용한다. missing에서는 객체목록 거리를 사용한다. 필터 설정을 임의로 고치지 않았다.

## MyTrack·당근·MPC로 전달되는 값

missing은 처음60m 경계의 far_acc_only 정책으로 객체 출력이 보류되다가7.25초에 비전 L1에서 front radar L1으로 넘어간다. 이때 실제 앞차18.70m/s·59.8435m지만, fused는19.9410m/s·59.9970m다. MyTrack은 새 출력 ID의첫갱신(cnt1)이므로 aLead0을 표시한다. DPath L1은19.9392m/s·59.9964m·aLead0·aLeadTau1.5를 받는다. 기존 비전의−5m/s² 감속 정보보다 낙관적인 레이더 값으로 넘어가는 단계다. 새로운 상태값은 정의하지 않았다.

MyTrack은 속도/거리를 같은 값으로 전달하고, 원형 관측기로 속도 변화에서 가속도를 구한다(`radar_tracks.py:120,158`). DPath는 현재 자차속도+vRel과 시각에 맞춰 투영한 거리를 사용한다(`primary.py:680`). 작은 투영 차이는 있지만 큰 낙관은 이미 fused에 있다.

| model 시각 | missing 기준 거리/속도 | missing fused 거리/속도 | missing MyTrack aLead | full fused 거리/속도 | full MyTrack aLead |
|---|---|---|---:|---|---:|
|8초|57.5636m /14.9500m/s|58.9272m /18.7094m/s|−1.9075|58.0793m /15.9893m/s|−4.4701|
|9초|50.4579m /9.9500m/s|53.2439m /15.3924m/s|−3.5243|51.9561m /11.3414m/s|−4.5627|
|11초|26.0414m /0m/s|30.5465m /6.8762m/s|−4.4968|33.3093m /2.2474m/s|−4.6089|

full/missing은 제동 명령이 달라 자차 위치도 달라진다. 따라서 **full 거리와 missing 거리를 직접 빼서 센서 오차로 부르면 안 된다.** 각 케이스의 기준 거리와 자기 필터값을 비교해야 한다.11초 full의 기준 거리는31.4652m다.

missing8초의 DPath 값은58.8841m /18.6956m/s다. MPC가1.1111초 뒤의 앞차 위치를78.2761m로 예측하지만 같은 가상 앞차의 기준 위치는71.0882m다. 이미 optimistic한 입력을 미래로 연장한다.11초 MPC 예측34.0129m 대 기준26.0414m에서도 차이가 남는다.

MPC 수렴용 거리 하한(`long_mpc.py:400`)의 추가 보정은 missing 지연0의13.65초에 처음0.0268m 나타난다. 첫 접촉은13.75초이므로 최초 필터 차이보다 훨씬 늦다. 이를 초기 원인으로 돌리지 않았다. 추가센서지연0.15초의 missing case에서는 접촉 전 이 보정이 나타나지 않아도 접촉했다.

모든 기록에서 native solver 상태0, CAN 디코딩 오류0, record CRC/sequence 오류0이다.0x80 raw→fused→MyTrack→DPath→MPC가 실제로 연결되었다는 증거와 장애물 회피 실패를 구분한다. 단위검사는 반복하지 않았고, 새 관찰 도구만 실제 실행했다.

## 실제 로그가 더 필요한 부분

이 결과만으로 실물 ECU의 fused 필터를 보수하거나 live를 켜지 않는다. 공개 템플릿의 불확실성47을 고정했고, 실제 ECU의 속도 잡음·대상 선택·측정 지연을 재현하지 않았기 때문이다. 추가 자료는 같은 물체를 시간으로 연결할 수 있어야 한다.

1. 이미 기록한 앞차 감속·정지·ACC 대상 소실 전후의 연속rlog. 예시 최소 구간은 사건 전5초+사건 후15초이며, 절단 없이0x80의106프레임·0x85·0x235·0x237과 bus/DLC/개별 수신시각을 포함한다.
2.0x235 STATE/TARGET_ID·가용성 변화와0x237 PRESENT/거리/횡위치/카운터를0x80의slot/age/uncertainty/거리/속도와 같은 시각으로 비교할 수 있는 자료. CHECK_BYTE를 검증할 실제 여러counter/대상 상태의 원본도 필요하다.
3.B4 휠속도·0x24 yaw와 carState.vEgo/aEgo를 동시에 포함한다.0x190 cycle clock와0x239 ECU timestamp가 있으면 ECU 측정시각과 CAN 수신/조립/모델시각의 관계를 추가 분석할 수 있다.
4.modelV2·liveTracks·radarState·longitudinalPlan·carControl와 카메라 기준이 함께 있어야 실제 거리/속도·제동 명령·차 반응을 분리할 수 있다. 실제 ECU/펌웨어 식별 자료가 별도로 필요하다.
5.자료 확보를 위해 실차에 실험 CAN을 보내거나 위험한 급제동을 새로 수행하도록 요구하지 않는다. 순정 PCS/AEB·운전자 개입·실제 제동력 검증은 별도 범위다.

실행은 고정 native snapshot을 지정한 뒤 `python acc_contract_diagnosis.py`다. 결과는 `acc_contract_diagnosis/summary.json`과8개 case JSON에 저장된다. raw·fused record는 첫 프레임 기준으로, MyTrack/DPath/MPC는20Hz model 기준으로 구분되어 있다.
