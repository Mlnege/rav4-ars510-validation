# 신호 준비·출발 금지·카메라 좌표 독립 검증 기록

최신 카메라 프로파일 수정은 오프라인에서 동작하며, 실물 영상의 빨강·초록 인식 정확도와 차량 안전성을 입증한 상태는 아니다. 원형 신호 처리는 주행 중 약 -0.5m/s²의 완만한 감속 준비와 정지 차량의 출발 금지를 제공한다. 이 기능만으로 빨간 신호 앞에서 완전히 정지한다고 보고하면 안 된다.

## 확인한 결함과 수정

제공 로그를 읽기 전용으로 조사하니 장치 프로필은 `tizi`, 전방 센서는 `ox03c10`이었다. `roadCameraState` 3,077건은 유효했고 저장소의 `DEVICE_CAMERAS` 설정상 해당 전방 카메라 크기는 1928×1208이다. 이는 실제 영상 버퍼의 픽셀 크기를 직접 읽었다는 뜻은 아니다. 로그에는 원본 이미지가 없어 버퍼와 렌즈의 물리적 특성을 별도로 확인하지 못했다.

기존 신호 추적 수신기는 1344×760 영상만 처리했고, 정지 준비 runtime은 카메라 설정이 1344×760인 경우만 허용했다. 따라서 제공 로그의 장치/센서 조합은 기존 조건에서 정지 준비 입력으로 사용할 수 없었다. 카메라 이름을 억지로 변경하거나 데이터 유효성을 강제하지 않고 다음 파일을 수정했다.

## 추가 CAN 연결에서 재현한 출발 금지 후 양수 출력

`native_signal_can.py`는 기존 장시간 실행기를 변경하지 않고, LongControl의 수치 출력을 실제 `CarController.update()`에 100Hz로 전달한다. 여기서 원형 주기로 생성한 `0x343 ACC_CONTROL` 33.3Hz 메시지를 메모리에서 `toyota_checksum()`과 실제 `CANParser`로 검증한 뒤 가상 차량 모형에 전달한다. `CarInterface.init()`·Panda·실물 송신에는 접근하지 않는다. 이 짧은 연결 검사를 신호→LongControl의 장시간 결과와 합산하지 않는다.

최초 `stopped_red_green_go` 사례에서는 2.15초에 출발 금지와 `plan.shouldStop`이 성립하고 LongControl이 -0.003을 출력했지만, 마지막 CAN 명령은 +0.623으로 남았다. 2.16초의 다음 정규 CAN 발행에서도 +0.502를 새로 생성했고, 2.19/2.22/2.25/2.28초에도 양수였다. 첫 음수 CAN은 2.31초의 -0.033이었다. 원형 Toyota rate-limit/PID 잔여 상태 경로가 원인 후보이며 파일 담당자가 해당 조건을 수정·검증 중이다.

이 실패에서는 양수 유지 16개 제어 틱 중 **새 양수 메시지가 5건**이었다. 다음 정규 발행까지 이미 보낸 명령이 1~2틱 유지되는 현상은 현재 33.3Hz 전송 주기의 물리적 한계로 별도 표시한다. 이를 없애려고 승인되지 않은 추가 CAN 메시지를 주기 밖에서 만들지 않는다. 새 검사의 성공 조건은 출발 금지 후 첫 정규 발행부터 양수가 없는 것이다. 명시한 모형에서 금지 기간 최대 속도는 0.081453m/s, 이동은 0.053764m였으며 이는 실물 측정이 아니다. 원본 실패 결과는 `native_signal_can/failed_hold_metrics.json`에 보존한다.

별도 확인 정책도 남아 있다. 실제 제어가 꺼진 2초 동안 빨강 관측을 주어도 기존 runtime은 StartGuard를 초기화한다. 제어를 켠 2.00초부터 빨강 확인이 시작되고 2.15초에 출발 금지가 성립한다. 확인 중 0.15초의 양수 요청, 다음 정규 발행까지의 명령 유지, 가정한 차량 응답 지연은 서로 구분해야 한다. 이번 송신기 정정으로 활성화 순간부터 어떤 움직임도 없다고 입증되는 것은 아니다.

주행 빨강 준비 사례의 최초 음수 시각은 계획 4.05초, 실제 원형 CAN 디코딩 명령 4.05초, 명시한 지연·1차 응답 모형의 가속도 4.34초였다. 모형 응답에는 0.15초 명령 지연과 앞선 양의 가속도를 줄이는 시간이 함께 포함된다. 실제 차량의 제동 응답 시각이라는 주장은 아니다.

파일 담당자는 exact RAV4 2022·직접 종방향·longActive·stopping·0 이하 요청에서만 양수 이전 요청과 PID 잔여 상태를 정리하고 최종 PCM 요청을 0 이하로 제한했다. 담당자 소유 파일은 `opendbc_repo/opendbc/car/toyota/carcontroller.py`이며, 원형 송신 주기는 보존했다. 소스 raw SHA256은 `f09cebd050f822a5c181f6c706cc3eb752c3f90bca24f5415a86b7506d502d97`이다. 담당자가 실행한 별도 24개 회귀는 주 담당자 보고에서 구분한다.

그 뒤 독립 재실행한 12사례는 모두 통과했다. 출발 금지 2.15초 후 다음 정규 CAN 2.16초부터 음수였고, 기존 명령 유지 1틱만 남았다. 새 양수 메시지는 0건이며 기존 주기 밖에 추가 생성한 메시지도 없다. checksum·DBC·출력 범위·매 3틱 정규 발행 검사·CP 불변·코드 지문 불변을 직접 확인했다. 입력/모형은 여전히 합성이므로 실물 PCM의 수락과 차량 안전성을 입증하지 않는다.

기존 7개 다른 사례의 공통 CSV를 수정 전후 비교하니 6개는 정확히 같았다. 같은 RAV4의 모델 정지 사례만 수정 범위의 stopping 상태에서 9.15초 이후 차이가 있었다. 최대 CAN 차이는 0.001m/s²(한 양자화 단위), 계획 목표 차이는 0.000111m/s², 가상 차량 속도 차이는 0.000325m/s였다. 수정이 RAV4의 일반 정지 요청에도 적용되므로 이 결과를 다른 7개가 모두 같다고 보고하지 않는다.

## 실시간 검사의 시간과 환경

최종 OX 작업은 2026-10-12 16:39:47.672~17:40:47.707 KST에 실제 3,660.035초 동안 완료했고 실행 프로세스 exit0을 직접 확인했다. 73,200계획·366,000 제어 호출, 의미적 위반/solver 오류 0, CP 305회 불변이었다. 최대 step은 36.403ms, 최대 RSS 74.582MB, 계획 목표 시각 뒤처짐 틱은 191개였다. 실제 20Hz 계획과 한 계획당 LongControl 5회를 실행했다. 이 5회는 한 50ms 안에 연속 호출하는 **가상 10ms 간격의 호출수** 검사이며 실제 벽시계 10ms 분산 실행을 입증하지 않는다. 결과는 `realtime_ox_final_61min/summary.json`에 보존한다.

시작 시각의 실제 입력 시간은 `VIRTUAL_NOW`를 1ns 단위 정수로 내린 값이고, IO 생성기의 실제 `logMonoTime`도 같은 내림 규칙을 따른다. 계산 시계만 가상 시간으로 읽으며 실시간 대기는 실제 `perf_counter` 시계로 50ms 간격을 맞춘다. 계획·CAN 상태·직렬화 후 제어 cadence를 검사한다. 파일 저장소와 Params·messaging IO만 프로세스 메모리로 격리하며 소켓 송신을 금지한다.

수치 모듈은 `build_snapshot_b0a5c630260ad76b` 고정 디렉터리에서 읽는다. 해당 디렉터리의 모듈은 검사 중 재빌드하거나 덮어쓰지 않는다. `launch_snapshot.json`에는 시작 때 선택한 코드 지문을 16:41:21에 외부 읽기 전용 절차로 추가 기록했다. 실행기 내부에서도 시작 지문을 읽어 최종 지문과 비교한다. 11개 코드 파일과 5개 `.so` 지문을 별도로 보존했다.

완료 직후 별도 읽기 전용 끝점 검증에서 선택한 11개 소스와 5개 수치 바이너리의 SHA256이 시작 지문/최종 보고와 일치하는 것을 직접 확인했다(`endpoint_verification.json`). 이 선택 범위는 신호→LongControl이며, 그 이후 수정한 CarController를 이 61분의 범위에 소급 포함하지 않는다.

앞서 실행한 두 작업은 최종 OX 61분 검사에 합산하지 않는다. 첫 작업은 219초/4,382계획 후 다른 작업의 수치 라이브러리 덮어쓰기와 겹쳐 종료됐고, 1ns 입력 생성 규칙 차이가 112건 있었다. `realtime_61min/interruption_diagnosis.json`에 실패/중단을 보존했다. 16:02:47에 시작한 OS 작업은 프로파일 수정 전 코드를 읽었으므로 최신 OX 변경의 장시간 검증으로 취급하지 않는다.

최신 CAN 보조는 `native_signal_can_paced.py`에서 원형 `LongControl.update()`의 인자·반환값을 바꾸지 않고 각 호출 앞에 실제 `perf_counter` 목표 시각의 10ms 대기를 넣었다. CarController는 같은 제어 틱에서 뒤따라 실행한다. 이는 시각/IO wrapper이며 수치 알고리즘 대체가 아니다. `realtime_can_wall_final_35min` 작업은 17:22:46.501~17:57:46.599 KST에 2,100.097초 동안 완료했고 exit0을 직접 확인했다. 42,000계획·210,000제어/Controller 호출·70,000 정규 ACC 메시지, 의미적 위반/체크섬/DBC/정규 3틱 주기/새 양수 hold 발행 0, CP 175회 불변이었다. 선택한 16개 소스와 5개 native 바이너리의 시작/종료 지문도 동일했다. 이미 보낸 양수 명령이 다음 정규 메시지 전까지 1틱 유지된 경우는 총 15회이며 새 양수 발행과 분리했다.

실제 제어 호출 간격은 최소 0.052319ms, p99 11.989881ms, 최대 332.833101ms였다. 1ms 초과 목표시각 뒤처짐은 42,057틱, 최대 뒤처짐 322.909628ms, 계획 lateTicks는 13개였다. 최대 step 벽시계 시간은 52.762499ms, 최대 RSS는 84.210938MB였다. 초기화/기록/OS 대기 등이 계산 밖의 지연에 포함될 수 있지만 원인은 아직 분리 측정하지 않았다. 완벽한 10ms 마감 준수나 실제 송신 33.3Hz 균일성을 주장하지 않는다. 정규 CAN 생성은 원형 매 3제어 틱 조건이며 소켓 송신은 없다. 이 35분을 기존 61분과 합산해 최종 전체 CAN 연결을 1시간 검증했다고 말하지 않는다.

기존 helper의 `ReplayClock`은 한 계산 단계 안에서 멈춰 있고 센서/발행 헤더도 같은 가상 시간에서 만든다. 따라서 관측 나이와 `processingDelay=0`은 실제 벽시계 지연과 다르다. 새 35분에서 제어 대기는 실제 시간으로 했지만 신호/서비스 나이는 여전히 가상 입력 기준이다. 이 차이를 실제 앱의 소프트웨어 보호 동작과 합쳐 판단하지 않으며, 별도 `TIMING_INVESTIGATION_PLAN.md`에 센서/헤더/수신/계산/IO/대기 원인분리 계획을 남겼다.

17:19:57에 먼저 시작했던 `realtime_can_final_35min`은 버스트 구조였으므로 약 2분 후 의도적으로 중단했다. 완료 결과로 사용하거나 뒤의 35분과 합산하지 않는다. 기존 61분 실행기와 원형 코어는 이 보조 작업을 위해 바꾸지 않았다.

## 남은 자료와 적용 제한

실물 카메라 입력 버퍼 크기와 전체 프레임 변환 여부를 장치에서 별도 확인해야 한다. 원본 주간·야간·눈부심·교차 방향·회전 차로 영상, 정답 신호 색/방향 표식, timestamp 정합 자료가 없으므로 빨강·초록 색 정확도, 잘못된 초록으로 출발 금지가 해제될 위험, 차로 관련성 정확도를 입증하지 못했다. 제공 로그에서 livePose 56건·calibration 39건이 유효하지 않은 경우도 있었으므로 신선도와 보정 실패 시 거절 조건을 유지했다.

이 작업에서 신호 기능의 실제 설정을 켜지 않았다. 실차 제어 메시지·PCS/AEB 설정·Panda 제한·운영 Params·`.env`·시크릿을 변경하지 않았다. CP와 안전 설정 불변 검사는 실제 native fixture에서 수행했지만, 이것으로 순정 PCS/AEB 보존이나 차량 안전성을 확인했다고 해석하면 안 된다. 레이더 객체 wire format/CRC 검증과 신호 인식 정확도 검증도 서로 다른 근거다.
