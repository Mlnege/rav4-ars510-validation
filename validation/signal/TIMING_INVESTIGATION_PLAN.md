# 시간 기준·실시간 지연 후속 조사 계획

현재 확인된 것은 오프라인 검사기의 시간 계약과 측정된 지연이며, 실차 제어 결함으로 아직 확정하지 않는다. 실제 앱의 수신/유효성/제어 활성화 계약은 별도 담당자의 원형 소스·클래스 검사와 합친 뒤 판단한다.

1. 기존 최종 61분/35분 작업과 게시용 소스는 끝까지 동결한다. 추가 계측은 새 작업 파일과 새 출력만 사용한다. 보통 계획의 오래된 목표값을 막는 코드나 software watchdog을 제안하기 전, 실제 앱의 `CC.longActive` 비활성화 경로까지 재현한다.
2. 가상 센서 시각, 실제 벽시계, 서비스 헤더의 `logMonoTime`, 마지막 수신 시각/프레임을 별도 기록한다. 현재 `ReplayClock`은 계산 중 멈춘 값이므로 느린 계산에도 runtime 나이와 publish `processingDelay`가 0으로 보일 수 있다. 실제 벽시계에 맞춰 증가하는 별도 IO 시계로 이 차이를 재현한다.
3. 새 계측기의 이름은 우선 `work/signal_validation/diagnostic_timing.py`로 한다. setup/입력 준비/원형 planner 계산/원형 LongControl 계산/원형 CAN 생성·디코딩/CSV 쓰기·flush/psutil/실제 sleep 깨움을 각각 `perf_counter_ns`로 측정한다. 알고리즘의 입력/반환값을 바꾸지 않는 시간/IO wrapper만 추가한다.
4. 새 객체 생성·준비를 12초마다 하는 현재 fixture와 한 번 준비한 객체를 유지하는 시험을 비교한다. 개별 step 최대 52.76ms보다 전체 제어 목표 뒤처짐 322.91ms가 큰 이유를 초기화, 기록 IO, 수치 계산, OS 대기로 나눠 확인한다. 단순히 OS나 알고리즘 탓이라고 가정하지 않는다.
5. 데이터가 오래되면 헤더만 새로 붙이지 않는다. 오래된 모델/관측의 body·헤더·수신 이력을 유지하고 실제 송신이 끊긴 서비스만 원형 수신/유효성 판단에 전달한다. 가능하면 원형 `SubMaster.update_msgs`를 소켓 IO만 격리해 실행하고 평균 주파수/나이 판정을 재사용한다. 실제 클래스 사용 범위와 필요한 함수 추출 범위를 명시한다.
6. 센서 중단과 계획 계산 지연을 서로 독립적으로 50/150/300/600ms에서 주입한다. carState/CAN은 계속 정상인 경우, 모델만 중단한 경우, longitudinalPlan만 중단한 경우, 관측 JSON만 중단한 경우를 구분한다. 신호 준비 200ms/출발 금지 확인 정책/서비스 alive/원형 제어 활성화/마지막 목표 유지/정규 CAN 메시지를 같은 시간표로 기록한다.
7. 제어 호출뿐 아니라 원형 CarController 계산 뒤 생성한 정규 CAN의 실제 벽시계 생성 시각도 새 wrapper로 기록한다. 기존 매 3틱 프로토콜 주기와 벽시계 지연·catch-up을 구분하며 추가 CAN 메시지로 보이지 않게 가리지 않는다. 가정한 차량 모형은 고정 10ms 적분과 실제 경과 적분을 별도 분석한다.
8. 비교군은 IO 기록을 끈 메모리 결과, 현재 CSV 기록, 객체 재사용/새 생성, 원형 가상 고정 시계/벽시계 IO 시계이다. 원형 안전 설정, 운영 Params, `.env`, 실차/Panda/PCS와 시크릿에는 접근하지 않는다. 현재 native `.so` 스냅샷도 변경하지 않는다.

검사의 결과는 실제 앱 계약, 오프라인 시간 alias, 기록/초기화 부하, OS 지연, 실제 계산 시간, 센서/계획 신선도를 별도로 보고한다. 색 인식과 실차 안전성은 영상·정답·실차 근거가 없어 계속 미검증이다.
