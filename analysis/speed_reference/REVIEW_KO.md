# 속도 기준 비교의 독립 검토

현재 결과는 **서로 다른 차량속도 기준으로 객체 속도를 계산하는 소스 계약 차이**를 보여 준다. 이를 센서 자체의 속도 오차, 최종 앞차 선택 실패, 근거리 정지 실패의 단일 원인으로 확정하면 안 된다. 특히 `inferred_point_ego_minus_latest_b4`에는 조립기가 실제 사용한 B4와 관측 도구가 미리 읽은 B4의 차이가 섞인다.

검토 중 관측 도구의 import 정리와 재실행이 있었으므로 최종 읽은 묶음을 기준으로 기록했다. 도구 SHA-256은 `f6a363d9b75a1319c6f5efd53e980280c9c10ab162dd2681e50cd6eb714ae890`, 결과 JSON은 `a5b9ad111a4174ace37c2b6ffe17945af1f35bfee578ba1eb0fb1433f23bce00`이며 JSON의 `probe_sha256`과 도구가 일치했다. 이 문서만 새로 작성했고 도구·코어·기존 결과는 수정하지 않았다.

## 소스에서 확인한 계약

| 단계 | 사용하는 값과 시점 | 근거 |
|---|---|---|
| 레이더 조립 | `CompletedRecord.time_s`는 완성 시각이 아니라 첫 프레임 시각 | `opendbc/car/toyota/ars510/transport.py:27`, `:69–74` |
| B4 갱신 | CAN 프레임을 처리하는 순서대로 캐시 갱신. 레이더 조립 중에도 갱신 가능 | `ars510/interface.py:231–247`, `:260–264` |
| fused 객체 계산 | 조립 완료 때 첫 프레임 시각으로 계산하되 그때 캐시된 B4 사용. freshness는 시각 차이의 절댓값으로 검사 | `ars510/interface.py:242–247`, `:288–295`, `:549–575` |
| 상대속도 | `vRel = fused v_long_ground − 사용한 B4 차량속도` | `ars510/interface.py:574–575` |
| 오프라인 어댑터 | `vLead`는 fused `v_long_ground`를 그대로 전달 | `ars510_offline.py:154–174` |
| MyTrack | 전달된 `radar_point.vLead`를 사용해 속도·가속·저크 필터 계산 | `opendbc/car/radar_tracks.py:68–71`, `:130–155` |
| CarState 차량속도 | B4가 아닌 네 바퀴 속도의 평균과 속도 필터 | `opendbc/car/toyota/carstate.py:86–94` |
| DPath snapshot | 전달된 `vLead` 대신 현재 `v_ego + vRel`로 재구성 | `radar_motion/primary.py:653–685`, 특히 `:680` |
| 실제 RadarD 입력 | 현재 구독한 CarState 속도와 레이더 객체 사용. 모델 측정 시각과 liveTracks 헤더 차이도 별도로 전달 | `carrot/radar/radard_dpath.py:120–134` |

따라서 `snapshot.v_lead − point.vLead = 전달한 CarState.vEgo − 객체 vRel에 사용한 B4`라는 항등 관계가 성립한다. 각 값의 획득 시점·필터·원래 차량 신호가 다르므로, 이 차이만으로 둘 중 어느 값이 실제 물리 속도의 정답인지 판정할 수 없다. 기존 fused 필터의 제조사 미확정 필드·보정값에 대한 추가 불확실성도 이 검사로 해소되지 않는다.

## 원본을 추가로 읽어 분리한 결과

추가 관찰은 작업용 Linux Python에서 원본 전체 스키마를 읽고 현재 원형 함수를 호출했다. `_payload` 호출을 프로세스 메모리에서 감쌌지만 원형 반환값을 바꾸지 않았고, 히스토리 초기화로 새 디코더가 생겨도 관찰되도록 클래스 호출을 추적했다. 원본 시각·프레임 번호·페이로드·식별자는 파일로 저장하지 않았다. 아래 개수는 어댑터의 완성 record 진단 개수와 일치했다.

| 항목 | log_1 | log_2 | log_4 |
|---|---:|---:|---:|
| 완성 record | 481 | 1,021 | 931 |
| 객체가 있는 완성 record | 182 | 117 | 6 |
| 출판된 객체 관찰 | 246 | 117 | 6 |
| 모델 시점의 measured snapshot 관찰 | 277 | 125 | 3 |
| 객체 계산에 사용한 B4가 record 시작보다 새로움 | 481 | 1,021 | 931 |
| 조립 소요 시간 p50 / p99 / 최대 ms | 31.228 / 48.171 / 49.029 | 39.542 / 42.091 / 47.105 | 39.803 / 42.522 / 42.954 |
| 사용한 B4가 record 시작보다 뒤인 차이 p50 / 최대 ms | 20.416 / 42.046 | 20.429 / 42.620 | 28.418 / 42.523 |

사용한 B4는 모든 record에서 완료 시각보다 같거나 앞이었다. 완료 시각에서 본 B4의 최대 오래된 정도는 30.163 / 32.010 / 31.862ms였다. 즉 첫 프레임 시각과 조립 완료 시각은 구분해야 한다. 소프트웨어의 record 첫 프레임 시각 자체가 레이더 ECU의 실제 측정 시각이라는 뜻은 아니다.

현재 도구의 `points=369`는 서로 다른 실물 객체 369개나 독립 출판 369번이 아니다. 한 record에 여러 점이 있고, 모델 시점에는 지난 레이더 결과가 다시 쓰일 수 있다. 객체가 있는 record는 305개, 모델 시점 measured 관찰은 405개다. 이 표본 단위를 바꾸어 해석하면 안 된다.

## 주의가 필요한 비교 두 가지

**1. 미리 읽은 B4와 실제 사용한 B4를 같은 값으로 취급하지 않아야 한다.**

도구는 한 CAN 묶음의 모든 B4를 먼저 읽은 다음 같은 프레임 목록을 어댑터에 전달한다(`speed_reference_probe.py:106–119`). 어댑터는 목록 순서대로 프레임을 처리하므로, 레이더 완성 프레임 뒤에 같은 묶음의 B4가 있으면 객체 계산 당시에는 아직 그 B4를 읽지 않았다.

실제 출판 객체 중 log_1의 1개와 log_2의 16개, 총 17개에서 이 차이를 직접 확인했다. 도구가 미리 읽은 B4와 디코더가 사용한 B4의 속도 차이 최대는 0.002778 / 0.038889m/s였다. 디코더 내부에서 `(v_long_ground − vRel) − 실제 사용한 B4`를 계산한 잔차 최대는 0 / 약 8.9×10⁻¹⁶ / 0m/s다. Cap’n Proto 출력 이후에는 Float32 반올림도 더해질 수 있다.

따라서 JSON의 `inferred_point_ego_minus_latest_b4` 최대 약 0.038889m/s를 디코더의 수치 오류나 센서 오류라고 부르면 안 된다. 이 항목은 **관측 도구의 최신 B4 캐시와 객체에 사용된 기준의 차이**다. 후속 도구에서는 실제 사용한 B4·그 시각·record 시작·완료를 따로 읽어 비교하는 편이 해석상 명확하다. 이번 검토에서는 도구나 값을 보정하지 않았다.

동일 헤더의 복수 B4가 다른 속도 값을 가질 때에는 `b4_rows.sort()`가 원래 프레임 순서를 보존하지 않을 수 있다. 이번 원본에서는 같은 헤더에 복수 B4 또는 중복 CarState 헤더가 0건이어서 이 정렬 문제가 관찰 수치에 영향을 주지는 않았다.

**2. 로그 저장 순서를 실제 앱 수신 순서로 취급하지 않아야 한다.**

모델 snapshot에 사용한 CarState 헤더가 모델 헤더보다 뒤인 관찰은 58 / 58 / 0개다. 최신 레이더 객체를 완성한 CAN 헤더가 모델 헤더보다 뒤인 관찰도 23 / 26 / 0개다. 이는 로그를 읽는 순서에서 이미 읽은 최신 상태와 오래된 모델 헤더를 비교한 결과다. 원본에는 해당 프로세스가 각각의 메시지를 실제로 받은 시각이 없다.

실제 앱도 모델 계산 완료·게시·구독 갱신 시점의 최신 CarState를 사용할 수 있다. 따라서 음수 `model_cs_age`를 시간 역행·센서 소실·잘못된 모델 헤더·미래 데이터를 이용한 실차 동작으로 확정하면 안 된다. 전체 서비스의 헤더 순서 역전 최대 598~894ms 역시 특정 센서의 지연 최대값으로 읽으면 안 된다.

현재 소스의 CAN 수신 C++ 경로는 `MessageBuilder.initEvent()`를 쓰며(`selfdrive/pandad/pandad.cc:108–120`) 이는 `CLOCK_BOOTTIME`이다. CarState Python 메시지는 `time.monotonic()` 헤더를 쓴다(`selfdrive/car/card.py:334`, `cereal/messaging/__init__.py:42–46`). 원본 장치의 실행 소스·절전 이력·시계 오프셋은 이 자료로 확정하지 못했다. 따라서 헤더로 정렬한 직전 B4/CarState 대조도 **수치상 시각 연결**이며 실제 동시 획득의 증명이 아니다.

독립적으로 모델 헤더보다 같거나 앞인 직전 CarState를 선택해 최대 100ms 범위에서만 수치를 대조했다. 원래 저장 순서의 상태와 값이 다른 snapshot은 16 / 69 / 0개였다. 이 비교에서 log_2 속도 차이 절댓값 최대는 약 0.108361m/s였고, 원래 결과의 절댓값 최대는 약 0.095456m/s였다. 차이가 남는다는 점은 확인했지만, 헤더 정렬 재생이 실제 앱의 수신을 더 정확히 복원했다고 주장하지 않는다.

## 속도·정지 해석의 범위

원형 snapshot과 전달된 `vLead`의 차이 절댓값 최대는 log_1 약 0.369951m/s, log_2 약 0.095456m/s, log_4 0m/s였다. B4와 CarState를 헤더상 직전 값으로 대조한 첫 5초 이후 최대는 약 0.375532 / 0.302946 / 0m/s다. log_2 전체 최대 3.261111m/s는 초기 구간에만 있었으며 초기 상태·신호 도착 등의 가능성을 분리해야 한다. 초기 차이의 정확한 발생 원인을 이 검토로 확정하지 않았다.

B4 SPEED와 바퀴 속도 평균은 다른 입력이고 CarState는 별도 필터도 거친다. `cs_raw_minus_b4`에도 차이가 있어 필터 한 가지로 모두 설명되지는 않는다. B4 원형 helper는 길이와 비트 해석만 수행하므로 독립 체크섬 검증이나 속도 신호의 실물 교정을 완료했다고 주장할 수 없다. 이 경로는 Python 디코더·원형 수치 계산이며 C/Cython CAN 파서 실행 성능 검사가 아니다.

0.3m/s 경계 비교가 다른 3개 관찰은 실제 정지 판정 실패 3건이라는 뜻이 아니다. MyTrack 정지 감지는 필터된 속도와 추가 차이 조건을 쓰고, DPath 앞차 선택은 거리·모델·시간 연속성 등의 조건을 더 사용한다. 도구는 snapshot의 속도만 비교했으며 전체 L1 선택을 재생하지 않았다.

근거리 기하 조건 후보는 405개 snapshot 중 0개다. 실제 DPath는 모델 시각으로 거리를 투영할 수도 있지만 이 도구는 기본 `time_delta_s=0`으로 snapshot을 만든다. 이미 확인된 앞차 ID·정지 이력·freshness·실제 최종 L1·근거리 유지 전이·재출발을 검증하지 않았다. **이번 실제 자료로 근거리 정지나 최종 앞차 선택에 영향을 주었다고 입증할 수 없다.**

원본 `longActive=True`는 0개다. 원본 CP는 오프라인 호출 전후 불변이었고 실차 송신은 없다. 이번 검토에서 속도 강제 보정, B4/CarState 대체, fused 필터 변경, live 등록 또는 레이더 사용 가능 플래그 변경을 하지 않았다.

검토 결론은 계약 차이와 비교 시점의 주의 사항을 확인했다는 것이다. 어느 기준을 채택할지 결정하려면 실제 수신 시각·동일 객체의 연속 관측·차량속도 기준의 실물 교정 자료가 필요하다. 현재 로그만으로 단일 근본 원인을 확정하거나 실제 제동 안전성을 주장할 근거는 부족하다.
