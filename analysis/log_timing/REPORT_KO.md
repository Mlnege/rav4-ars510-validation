# 원본 로그의 카메라·모델·계획 시각 연결 관찰

실제 제어가 꺼진 원본 로그에서 모델·계획 2,792개를 카메라 프레임과 정확히 연결했다. 약 0.8초의 최대 차이는 각 로그의 첫 모델 한 개에만 있으며, 같은 모델의 기록된 실행 시간도 약 0.75~0.80초였다. 이후 모델의 촬영 종료→메시지 헤더 차이 최대는 50~59ms다. 초기 추론 시간이 긴 현상과 일치하지만 내부 초기화·컴파일 등 세부 원인은 확정하지 않았다.

수치들은 원본에 기록된 **시각의 차이**다. 서로 다른 시계 기원이 섞일 수 있고 EOF 자체도 현재 소스에서 센서 읽기 시간을 더한 추정치이므로, 물리적인 촬영 종료부터 실제 차량 제동까지의 지연으로 해석하면 안 된다.

## 읽은 범위와 소스 의미

완전한 Cap’n Proto 스키마로 4개 로그를 직접 읽었다. 원본 시각·프레임 번호는 정확한 연결을 찾는 메모리 키로만 사용했고, 결과에는 익명 로그별 개수·누락·부호·상대 밀리초 통계만 저장했다. 영상, 예측 배열, 위치, VIN, 장치 식별자, 경로, 계정, 설정 값은 접근하지 않았다. CAN 파서는 호출하지 않았다. 다른 검사의 CAN 구현 명칭은 `BACKEND=python`, MPC는 별도 C/Cython 구현이며 이 관찰에서는 MPC·안전 제어기를 실행하지 않았다.

현재 소스 기준 커밋은 `0e4ee1bdbef3ad7284b136fddf31592e3f8a785f`다. 수정된 현재 파일을 포함한 실제 관찰 시점의 소스 SHA-256은 `observations.json`에 있다. 이 현재 소스와 원본 장치의 실행 소스가 완전히 같다는 증거는 없다.

| 항목 | 실제 필드와 의미 | 현재 소스 근거 |
|---|---|---|
| 카메라 노출 시각 | 커널 SOF `BOOT_TS`에 센서 읽기 시간을 더한 추정 EOF | `system/camerad/cameras/spectra.cc:1418`, `:1566–1584` |

| Python 메시지 헤더 | `time.monotonic()`으로 생성 | `cereal/messaging/__init__.py:42–46` |
| 모델 내용 | 주 카메라 VIPC의 `frameId`·`timestampEof`를 복사. 주 카메라는 road 또는 wide 선택 가능 | `selfdrive/modeld/modeld.py:264`, `:520–522`, `fill_model_msg.py:76–87` |
| 모델 실행 시간 | 현재 소스의 `perf_counter()`로 `model.run()` 전후를 측정 | `selfdrive/modeld/modeld.py:476–498` |
| 계획 내용 | `modelMonoTime`은 모델 메시지 **헤더**를 복사, `processingDelay`는 계획 헤더−모델 헤더 | `selfdrive/controls/lib/longitudinal_planner.py:464–476` |
| 위치 필터 내용 | `livePose.timestamp`는 필터 시각. 카메라 EOF−100ms 또는 입력 센서 시각으로 필터가 갱신될 수 있음 | `selfdrive/locationd/locationd.py:33`, `:106–108`, `:126–128`, `:170`, `:250` |

| 제어 명령 참조 | `CarControl.longitudinalPlanMonoTime` 필드는 현재 스키마에 **없음**. `controlsState.modelMonoTime`이라는 정확한 이름의 필드도 없음 | `opendbc/car/car.capnp:433`부터, `cereal/log.capnp:850`부터 |

Linux 현재 C++ 카메라 경로는 `CLOCK_BOOTTIME`, Python 헤더는 단조 증가 시계 계열을 사용한다. 절전 후 두 기원의 차이가 생길 가능성은 있지만, 이 로그만으로 실제 절전·시계 오프셋·센서 소실 원인을 확정할 수 없다. `livePose.timestamp`도 게시 헤더를 복사한 값으로 취급하지 않았다.

| 익명 로그 | road / wide 카메라 | 모델 / 계획 | livePose | CarControl / controlsState | 정확 카메라→모델→계획 |
|---|---:|---:|---:|---:|---:|
| log_1 | 671 / 671 | 623 / 623 | 623 | 3,354 / 3,354 | 623 |
| log_2 | 1,203 / 1,203 | 1,019 / 1,019 | 1,019 | 5,997 / 5,997 | 1,019 |

| log_4 | 1,203 / 1,203 | 1,150 / 1,150 | 1,149 | 6,007 / 6,007 | 1,150 |

모든 모델의 `frameId`와 EOF가 roadCameraState의 두 값에 동시에 정확히 일치했다. 같은 번호의 wide 프레임은 있었지만 EOF까지 일치하지 않아 주 촬영 연결로 사용하지 않았다. 모든 계획의 모델 참조도 실제 모델 헤더에 정확히 일치했다. 유사 시각의 메시지를 임의로 대응시킨 결과는 아니다.

log_3에는 대상 메시지 자체가 없다. 이는 해당 서비스의 시각 값이 0이라는 뜻이나 카메라 고장 증거가 아니다. 나머지 모델·카메라·계획 헤더 및 모델 EOF의 0·역행·미래 참조는 0건이다. 단, 카메라 EOF가 자기 게시 헤더보다 큰 사례는 아래에 따로 표시한다.

## 전체 상대 시각 통계

단위는 ms이며 표는 `p50 / p95 / p99 / 최대` 순서다. 전체 통계에는 각 로그의 초기 한 개도 포함된다.

백분위는 `NumPy.percentile`의 기본 선형 보간을 사용한다. 처음 1초처럼 표본이 적고 큰 초기값이 한 개 있는 구간의 p99는 관찰된 개별 표본 값과 같지 않을 수 있다.

## 첫 모델 이후 상대 구간

각 로그의 **첫 모델 헤더를 0초**로 두었다. 처음 5초는 처음 1초를 포함한다. `p99 / 최대`만 표기하며 단위는 ms다. 계획도 연결된 모델의 같은 구간으로 분류했다.

100ms를 넘는 모델−EOF는 로그별 정확히 1개이며 모두 첫 모델이다. 같은 첫 모델의 `modelExecutionTime`은 752.810 / 801.013 / 753.814ms다. 전체 실행 시간의 p50은 25.595 / 24.621 / 23.828ms, p99는 30.530 / 30.731 / 28.806ms다. 이 기록은 초기 모델 실행에 시간이 든 현상과 일치한다. 실행 시간 필드와 서로 다른 시계의 차이를 빼서 실제 카메라 대기 시간을 확정하지 않았다.

참고로 모델 헤더−추정 EOF에서 기록된 실행 시간을 뺀 잔차는 log_4에서 4개가 음수다. 이 잔차는 실제 큐 대기 시간으로 정의된 필드가 아니므로 음의 물리 지연이나 잘못된 원본 모델 헤더로 판정하지 않았다.

모든 구간의 모델 `frameDropPerc`는 0%였고 `frameAge`도 0이었다. 그러나 연속 모델 번호 사이에는 로그별 한 번, 16 / 17 / 16개 번호가 관찰되지 않았다. road·wide 메시지의 번호는 전부 연속이었다. 따라서 `frameDropPerc=0`만으로 모든 촬영 프레임이 모델 출력으로 게시되었다고 주장할 수 없다. 현재 소스는 초기 10번 프레임 드롭 필터를 0으로 두고, 놓친 프레임이 있으면 준비 실행만 수행할 수도 있다(`modeld.py:451–462`). 이 소스 정책이 원본의 누락을 실제로 일으켰는지는 미확정이다.

| 항목 | log_1 | log_2 | log_4 |
|---|---:|---:|---:|
| road EOF가 자기 헤더보다 큰 개수 | 48 | 0 | 172 |
| road 미래 방향 차이 p99 / 최대 ms | 8.517 / 13.471 | 표본 없음 | 4.444 / 10.404 |
| wide EOF가 자기 헤더보다 큰 개수 | 11 | 1 | 122 |
| wide 미래 방향 차이 p99 / 최대 ms | 2.316 / 2.330 | 1.406 / 1.406 | 1.479 / 13.766 |
| livePose 무효 메시지 수 | 17 | 20 | 19 |
| livePose 필터 시각 0 수 | 18 | 21 | 20 |
| 그중 유효 표시인데 필터 시각 0 | 1 | 1 | 1 |
| livePose sensorsOK=True 수 | 623 | 1,019 | 1,149 |

카메라의 음수 헤더−EOF는 원본 관찰이다. 현재 소스의 EOF 읽기 시간 추정, 게시 순서, 실제 시계 기원 등의 가능성이 남아 있다. 동일 시계의 잘못된 타임스탬프나 시계 오프셋으로 확정하지 않았다. 모델·계획·0을 제외한 livePose 필터 시각에서는 미래 방향 헤더 차이가 없었다.

livePose의 `sensorsOK=True`는 원본 메시지의 표시값이다. 0 시각과 무효가 겹치는 초기 표본이 있지만 센서 소실이나 올바른 물리 센서 동작을 입증하지 않는다. `inputsOK=True`는 로그별 608 / 999 / 1,130개이며 `posenetOK`는 전부 True였다.

## controlsState의 출처 연쇄

| 항목 | log_1 | log_2 | log_4 | 합계 |
|---|---:|---:|---:|---:|
| 계획 참조가 0 | 241 | 902 | 264 | 1,407 |
| controls→계획→모델→동일 카메라 정확 연결 | 3,113 | 5,095 | 5,743 | 13,951 |
| 같은 controls의 최신 모델과 계획 출처 모델이 같음 | 2,884 | 4,614 | 5,458 | 12,956 |
| 같은 controls의 최신 모델이 계획 출처보다 새로움 | 229 | 481 | 285 | 995 |

차이가 난 995개 모두 `lateralPlanMonoTime` 쪽 모델이 더 새로웠다. 두 모델 헤더 차이의 p50은 51.912 / 49.643 / 50.607ms다. 서로 다른 프로세스의 최신 메시지를 구독하는 소스와 일치하는 관찰이다. 같은 제어 상태 메시지에 있는 최신 모델 참조를 해당 종방향 계획의 모델 출처로 대신 사용하면 약 한 프레임 다른 연결이 될 수 있다. 이것만으로 동작 결함이나 실제 제동 지연이라고 판정하지 않았다.

## 한계와 재현

CarControl 15,358개 모두 `enabled=False`, `longActive=False`, `latActive=False`다. selfdriveState 15,398개도 전부 비활성이다. 이 결과는 원본 제어 **비활성** 상태의 게시 시각·참조 연결 관찰이며, 실제 제어 활성 상태의 제동 성능·CAN 송신 간격·액추에이터 응답을 보증하지 않는다.

기존 소스 감시 장치에 조건을 주입한 54개 검사와 범위가 다르다. 그 검사는 합성 조건에서 감시 로직이 반응하는지를 확인하며, 이 관찰은 실제 원본 메시지의 시각을 읽는다. 어느 결과도 원본 센서 소실·시계 오프셋 원인이나 실차 안전성을 확정하지 않는다.

관측 도구를 Linux 작업용 Python 3.12에서 직접 실행했고 완전 스키마 읽기가 끝났다. Windows Ruff 검사도 통과했다. 새 폴더 밖의 소스·로그·빌드·설정은 수정하지 않았다. 사용자 인계 기록도 파일 범위 제한에 따라 따로 수정하지 않는다.

```powershell
wsl -d Ubuntu -- env PYTHONDONTWRITEBYTECODE=1 $LAB/work/linux_runtime/venv/bin/python $LAB/work/log_timing_observation/observe_timing.py
work/venv/Scripts/python.exe -m ruff check work/log_timing_observation/observe_timing.py
```

위 명령은 기존 작업용 환경과 제공된 로컬 입력 로그가 있어야 한다. 출력은 `observations.json`으로 제한되며 원본 시각·프레임 번호를 덤프하지 않는다. 전체 숫자와 누락·유효 여부는 JSON의 익명 통계를 확인하면 된다.
